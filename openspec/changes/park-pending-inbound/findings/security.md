# Security review: park-pending-inbound

Dimension: **security** only. Reviewed `dialectica-core/src/parked.rs` and
`dialectica-core/src/delivery.rs` at `30b9d14f`, against `design.md` and
`specs/op-transport/spec.md`. Bounds and shedding, reachable panics, parked data
readable as an op, the receive window and what survives a restart were each
checked. The overlay's two standing rules apply: an inbound message is never
trusted, and a reachable panic is a denial of service.

- [ ] **`spec-writer`** — `parked.rs:384-394` (`plan_park`, the own-channel check) — a first-come flood on a channel being opened locks every later honest message on that channel out of the parked store, and nothing in `design.md` records it
      **Scenario:** a peer is in a Stoa and restarts. Delivery replays that Stoa's backlog on its channel while startup's `channelCreate` is unanswered. The Stoa's id is public, so its channel id is computable, and anyone who can publish to that channel sends 256 minimal messages (or 54 of 150 KiB, which reach the 8 MiB bound) just ahead of the replay. Each of the honest replayed messages that follows meets `own.len() + 1 > per_channel_count` (or the byte bound), is discarded and logged as "discarded from the parked messages". SDS already counts each one delivered, so none is ever re-sent. The honest backlog on that Stoa is gone for this peer. This is the exact race the change exists to close, reopened by a 256-message flood. Cost to the attacker is trivial, and the flood is judged by nothing, because "Parking judges nothing".
      **Why it is a finding and not a style point:** the spec mandates "that payload MUST be discarded, and nothing already parked is", so the code is faithful to it, but the trade is not argued anywhere. `design.md` Decision 4 says "for ordinary traffic the count binds first", which answers honest volume and not a hostile one. Risks / Trade-offs lists the 32 MiB of attacker bytes on disk and says nothing about the per-channel lockout. A bound that is too small is described as showing up as "discarded" lines, which reads as tuning, when the same lines are the attack's signature.
      **Severity:** medium. Availability of honest data, and permanent loss, but bounded to the channels being opened, and the rule is the owner's. **Needed:** the owner decides whether first-come-wins is acceptable (then Risks must say so, and say what an operator sees), or whether the per-channel rule should evict the oldest parked message, or reserve part of the bound. The code does not change until the spec does.

- [ ] **`dev-writer`** — `parked.rs:407-435` (`plan_park`, the count loop then the byte loop) — an eviction made to restore the count bound is kept when the byte loop then discards the arrival, so one arrival costs two messages
      **Scenario:** `SMALL` bounds (3 / 300 B per channel, 5 / 500 B in all). Held: `a` 1 B; `b` 150 B, 150 B; `d` 99 B, 99 B (5 messages, 499 B, the count bound reached). Park `c` with 300 B (within its own channel's bounds). The count loop sheds `d`'s newest to make room. The byte loop then finds `c` holds as many bytes as `b` and, counted as the newest of all, is chosen, so `c` is discarded. Run as a probe test against this tree: `Parking { parked: false, evicted: 1 }`, and `d` is left with one message. An honest message on `d` was evicted for an arrival that was then not parked.
      **Amplification:** an attacker on a small channel with one 150 KiB message evicts one honest message from the channel holding the most, and loses nothing it cared about. The spec's "when the message chosen is the payload being parked, it is discarded and nothing more is" can be read as forbidding exactly this, since the evictions are "more". It is ambiguous, so the reading needs deciding.
      **Fix shape:** decide the arrival's fate against both bounds on the held rows first (a dry run on `kept`) and apply no eviction when the arrival is the one to go. `plan_park` is pure, so the test is a table.
      **Severity:** low. Needs both total bounds near full, and the loss is one message per attacker message.
      **Measured:** `cargo mutants` on `parked.rs` (35 caught, 15 unviable, 0 missed, tests `parked::` only) did not see this: the property is not mutated, it is missing.

- [ ] **`dev-writer`** — `delivery.rs:1433` and `parked.rs:154` (`Processor::park` opens the store per message) — each attacker message costs a file open, a schema transaction, a full scan of every held row and an fsync'd commit, on the one thread that decides every Stoa's messages
      **Scenario:** a flood on a channel being opened. The queue holds 256, so the flood is bounded in memory, but the processor spends the park cost per message, and every honest message behind it in the queue waits. The queue sheds the flood channel's newest, so honest messages are not lost, only delayed, for as long as the flood continues and the open is unanswered (35 s per `channelCreate` call, serial per Stoa at startup).
      **Measured:** 1000 sequential `ParkedStore::open` + `park` calls on a tmpfs temp directory, debug build: 5.19 s, 5.2 ms per park. tmpfs makes fsync nearly free, so this is a floor and a real disk is slower; SQLite's default journal mode and `synchronous=FULL` make each commit several fsyncs. Nothing in the tree measures it.
      **Severity:** low. Latency, not loss. `design.md` Risks names the open per held answer and not the open per park. **Needed:** either hold one connection for the processor's life (the design rejects it for staleness, which is a decision to revisit with this number), or set `synchronous` lower for this file, which still survives a module stop, the only restart the spec asks for, and say which.

- [ ] **`dev-writer`** — `parked.rs:203-239` (`create_schema`), `parked.rs:285-310` (`take_channel`) — the file never shrinks and freed pages keep attacker bytes after a review has decided them
      **Scenario:** a flood fills the 32 MiB total, the opens settle, and every channel is taken. SQLite returns the pages to its freelist and keeps the file at its high-water size, with the payload bytes still in them (no `secure_delete`, no `auto_vacuum`).
      **Measured:** parking 1000 messages of 1 KiB across four channels, then `take_channel` on each: file 1,396,736 bytes before and 1,396,736 bytes after, nothing parked. At the bound that is 32 MiB of host persistence for good, from one flood.
      **Why it matters here:** `design.md` Risks says "a channel's share goes when its open settles", and the module doc says what is parked "is kept apart" and gone once decided. On disk it is neither gone nor smaller. The bytes are attacker-chosen and unverified, and the file is the only place they outlive their review.
      **Severity:** low. **Fix shape:** `PRAGMA auto_vacuum = FULL` before the table is created in `create_schema` (the file is new, so no migration), and `PRAGMA secure_delete = ON` if the bytes matter; or delete the file when the last row goes.

## Areas checked and clean

- **Parked data readable as an op.** Parked rows live in `parked.sqlite`, opened only by `Stores::parked()`, which only `Processor::park` and the review path call. No code in the tree refers to the file other than `parked.rs`, `delivery.rs` and `lib.rs`'s `pub mod`, and nothing uses `ATTACH`. The table has no sender or timestamp column, checked by name in `check_layout` and by a test. The separation is by construction, as the design says.
- **Reachable panics.** No `unwrap`, `expect` or indexing outside `#[cfg(test)]` in `parked.rs`. Integer sums use `saturating_add` or `u64` over at most a few thousand rows. `kept.remove(at)` follows an `enumerate`, `*requests -= 1` is guarded by `> 1`, `rposition` and `max_by_key` results are matched, and `shed` returns `Option`. The processor wraps each park, review and judged message in `catch_unwind`; the book's lock recovers from poison. Hostile `LENGTH` values would need a tampered file.
- **Shedding across channels.** One channel cannot crowd out another beyond what it holds: over a total, the channel holding the most gives up its newest, and the arrival's own channel loses a tie. The queue's `offer` and `plan_park` share `shed`, and `newest` is unique per channel, so the choice is deterministic. Both loops terminate: each iteration removes a row or returns. A flooded channel that is not the largest is the only way to push another Stoa's messages out, and it needs the total at its bound (about four full channels), as the spec's rule intends.
- **Restart.** `held_rows` reads the persisted rows, so a restored store counts towards all four bounds. Startup's review is queued before the subscription and before any open can settle, takes `known` at the event, and leaves channels startup opens for their own review. A review that cannot read leaves the rows parked.
- **Receive window.** The clock is read per message in `pass`, at judgement, and a parked message is judged with an empty sender and zero timestamp that `receive_via` never reads. A long park cannot admit an op past `now + 1 h` as judged, so Lamport poisoning is held to the same bound as a live op.
- **Ordering and exactly-once.** `settle` and `take` share one lock, a waiting review is returned before any waiting payload, `take_channel` deletes in the transaction that reads, and one processor thread parks and reviews. A message parked before a settle is written before the review that reads it. No path was found that decides a message twice, or leaves one parked on a channel that has settled.
- **Logs.** No `Note` carries a payload, a sender identifier or a channel identifier; `NotParked` and `ReviewUnreadable` carry SQLite's own error text.
- **Mutation.** `cargo mutants --in-place` on `parked.rs`, tests narrowed to `parked::`: 50 mutants, 35 caught, 15 unviable, 0 missed. `delivery.rs`, narrowed with `--re` to `ChannelBook|Channels|InboundQueue|Processor|refused_on_hand_over|Opening` and tests to `delivery::`: 59 mutants, abandoned past the time budget after 27 were tested (21 caught, 6 unviable, 0 missed); the other 32 were not run. A whole-crate test run is 44 s a mutant, so the narrowing is mine. The tool cannot see a `const` (the bounds, pinned by a test instead) or a property that is missing, as the second entry shows.
