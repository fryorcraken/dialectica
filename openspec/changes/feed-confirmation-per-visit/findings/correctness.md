      **Scenario:** type "meant for A" in Stoa A's feed composer, click "All Stoas", open Stoa B, click "Publish the post": `publish_post` goes out with B's address and A's text (the pinned test does exactly this and asserts it). The reply composer has the same shape: one instance, `parentOp` follows `threadId`, so a reply drafted under thread X is submitted as a reply to thread Y. An op is signed and permanent, so the author cannot take it back from the wrong forum. This change neither introduces nor worsens it (the draft is deliberately left alone, and the spec says so), so it is not a defect of this diff. It is a defect in what the diff leaves behind: the test's own comment calls it "very probably a defect", `gh issue list --search "draft Stoa composer"` returns nothing, and per the flow GitHub Issues are the only place scope lives. Severity: medium, pre-existing. Needed: file an issue and decide which Stoa or thread a draft belongs to (spec first), or record that the owner has chosen to keep the behaviour. The reply-composer half is untested; the issue should say so.
      **Measured:** read-only. The pinned test passes on this tree (21 of 21 in `tst_publish_outcome_visits.qml`), which confirms the behaviour is real rather than inferred.

### Reviewed and clean

- **No behaviour I could break in the fix itself.** I traced every `enterOnly` transition against the `stateNames` order (`previewing`, `chosen`, `reading`, `moderating`) to see what `screenShown` reads at each intermediate assignment: list to feed, feed to thread (reads "list" for one instant, then "thread"), thread to feed, feed to moderation and back, feed to list via `acquireIdentity`, and a repeated `open()` while already on the feed (no change, so no spurious visit). In none does `screenShown` read "feed" or "thread" transiently on a path that leaves it again, so the hook cannot withdraw an outcome in the middle of the visit that produced it. The comment in `Main.qml` that a passed-through screen loses nothing a user could see holds.
- **No race with a late reply.** `Core.publishPost` and `Core.publishReply` are synchronous (`DComposer.submit()` documents it), so an outcome can never be written by a publish that began on an earlier visit.
- **`clearOutcome()` and the hook null-safety.** `composer` and `replyComposer` are always instantiated (the gate only toggles `visible`), so `beginVisit()` never reaches a null id. `onScreenShownChanged` cannot fire before `feed` and `thread` exist: no test or code path gives `Main` an initial `chosen` or `reading`, and neither is a bound property. `outcome` and `outcomeDetail` are plain properties with no binding for `clearOutcome()` to break. A stale `outcomeDetail` left behind would be invisible anyway, since `DPublishOutcome` is `visible: outcome !== ""`.
- **Within-visit retention** holds by construction: nothing in `reload()`, paging or the show-hidden toggle touches the composer, and the re-read after a publish is `onPublished: screen.reload()`.
- **Gates run on this tree:** `sh dialectica-ui/tests/run-qml-tests.sh` (whole suite, 28 spec files, no failures reported), `tst_publish_outcome_visits.qml` alone (21 passed), `check_qml_names.py`, `check_qml_reachable.py` and `check_qml_members.sh` all report ok. I did not run the `tst_check_*` self-tests of the gates, and no Rust is touched.
