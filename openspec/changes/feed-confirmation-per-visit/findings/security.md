# Security review: feed-confirmation-per-visit

Dimension: security only. Diff reviewed: `git diff origin/main...HEAD`.

- [ ] **`spec-writer`** — `dialectica-ui/src/qml/FeedScreen.qml:1055`, `dialectica-ui/src/qml/DComposer.qml:57` (`draft` is `field.text`) — a draft typed in one Stoa follows the user into another and is published there, under their signature, permanently.
      **Scenario:** user types "meant for A" in Stoa A's composer, clicks "All Stoas", opens Stoa B. `FeedScreen.composer` is one instance for every Stoa and `beginVisit()` clears only `outcome`/`outcomeDetail`, so B's composer shows "meant for A" and its enabled "Publish the post" button sends `publish_post{stoa: B, body: "meant for A"}`. `test_a_draft_typed_in_one_stoa_is_still_held_and_published_in_another` reproduces exactly this. Ops are signed and the system has no delete (`DComposer.qml` comments, "The cost of getting it wrong is permanent"), so a misdirected publish is visible to every peer in B forever. In a forum whose point is separate communities with separate moderators, text written for one audience reaching another is an integrity and disclosure risk, not only a UX gap.
      **Why it is a finding for this change, and not only a known note:** the behaviour pre-dates the change and this change does not make it reachable; severity is **low to medium** and it is **not a regression**. But the change edits exactly this boundary (what a visit carries over), records the defect as "very probably a defect rather than a choice" in a test comment and in `design.md` Decision 2, and then leaves it with no tracked home. `gh issue list --state all --search draft` returns no issue for it. A defect recorded only inside a `NO SPEC` test and a `design.md` that moves to the archive is one nobody will look for once this piece merges. The visit mechanism this change adds is the natural place to fix it (one more line in `clearDraft()` from `beginVisit()` or a draft-belongs-to-Stoa rule), so the spec decision is cheap now.
      **Act:** open an issue for it before merge (or decide it into the spec here) and cite it from the `NO SPEC` test. I do not ask for the fix to be bundled; I ask that it not be left untracked.

- [ ] **`tester`** — `dialectica-ui/tests/tst_publish_outcome_visits.qml:675` — the reply composer's cross-thread draft carry-over is not pinned, and it is the worse half of the same hazard.
      **Scenario:** `DThreadScreen.replyComposer` keeps one instance across threads and its `parentOp` and `stoaAddress` follow `screen.threadId` / `screen.stoaAddress`. A reply draft typed under thread X is still in the field when thread Y (same or another Stoa) is opened, and submitting publishes `publish_reply{stoa, parentOp: Y's root, body: <X's text>}`. The reply is attached to the wrong post as well as possibly the wrong Stoa, which also misrepresents what the author was answering. `design.md` Decision 2 says "That one is not tested", so the gap is acknowledged and no test would flip when the spec decision is made.
      **Measured:** not mutated. Nothing in `tst_publish_outcome_visits.qml` asserts the reply `publish_reply` arguments after a thread switch (the file's only draft tests are the two feed ones, lines 657 and 675).

## Clean areas

- **Outcome withdrawal cannot be skipped by another call path I could find.** Every route onto the feed or thread passes through `enterOnly`, which changes `screenShown`; `closeThread` and `closeModeration` reach the feed via the transient `"thread"` / `"moderation"` value and then `"feed"`, so `onScreenShownChanged` fires. No route re-points `chosen` at another Stoa while `screenShown` stays `"feed"` (`onJoined` only reloads the list). The residual risk, a future route that does, is recorded in `design.md` Risks and is a design decision, not a defect here.
- **No state is added that an attacker could influence.** `clearOutcome()` and `beginVisit()` take no argument and read no peer data; the diff adds no core call, no parsing and no allocation sized from input. `objectName` is derived from the constant `kind`, not from content.
- **The stale-claim hazard the issue names is closed.** The "saved on this machine" confirmation was a claim about an action the user did not just take; it is now withdrawn on every visit change, and the in-visit persistence (`publishing` is synchronous, the re-read does not touch the composer) means a stored outcome is never shown for a publish from a different visit.
- **No new dependency, no new file outside `dialectica-ui/` and the change folder, no change to the core API or wire shapes.**
- **Not reviewed:** correctness of the test fixtures, test strength and mutation results, which belong to the other reviewers.
